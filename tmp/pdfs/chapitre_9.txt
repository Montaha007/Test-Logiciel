Introduction
Cas de Apple, février 2014 (CVE-2014-1266)
◦ Dans la bibliothèque TLS d'iOS et de macOS, une ligne « goto 
fail; » est dupliquée par erreur
◦ Le second « goto fail; » s'exécute toujours : la vérification de 
la signature du serveur est sautée, et la fonction renvoie err = 
0, c'est-à-dire « succès »
◦ Conséquence : un attaquant placé entre le client et le serveur 
peut se faire passer pour n'importe quel site HTTPS
Ce qu'aurait montré la boîte blanche
◦ Un rapport de couverture des instructions aurait affiché en 
rouge les lignes qui suivent : elles ne sont jamais exécutées, 
quel que soit le test
◦ Le compilateur pouvait aussi signaler ce code inatteignable 
(option -Wunreachable-code de Clang)
Extrait simplifié du code C en cause
if ((err = SSLHashSHA1.update(&ctx, &serverRandom)) != 0)
    goto fail;
if ((err = SSLHashSHA1.update(&ctx, &signedParams)) != 0)
    goto fail;
    goto fail;      /* ligne dupliquée */
if ((err = SSLHashSHA1.final(&ctx, &hashOut)) != 0)
    goto fail;
err = sslRawVerify(...); /* signature */
...
fail:
    SSLFreeBuffer(&signedHashes);
    return err;     /* err vaut 0 : succès */
Les tests fonctionnels passaient : une connexion à un vrai serveur 
réussit. Seule la structure du code révélait le problème.

Introduction : le test boîte blanche
Définition (ISTQB)
◦ Technique de test fondée sur la structure interne de l'objet de test : code, architecture, flux de données. On dit 
aussi test structurel
◦ Elle désigne des éléments à couvrir (instructions, branches, conditions...) => couverture = éléments exercés / 
éléments identifiés
Boîte noire et boîte blanche
◦ Boîte noire (chapitre 8) : les tests viennent de la spécification => trouvent les fonctions manquantes ou fausses
◦ Boîte blanche : les tests viennent du code => trouvent le code jamais exécuté et les chemins jamais essayés
Démarche recommandée
◦ 1. Concevoir les tests boîte noire ; 2. mesurer la couverture du code ; 3. analyser chaque partie non couverte ; 4. 
compléter les tests

=== PAGE 6 ===
Introduction : valeur et limites de la boite blanche
Valeur (CTFL v4.0)
◦ Toute l'implémentation est prise en compte, même quand la spécification est vague, incomplète ou dépassée
◦ La couverture mesure objectivement ce que les tests ont exercé => elle montre où ajouter des tests
◦ Elle s'applique aussi au test statique : relecture du code, exécution à la main d'un algorithme ou d'un pseudo-code
Limites
◦ Trouver le code absent : une exigence jamais implémentée n'a aucune ligne à couvrir
◦ Garantir l'absence de défauts : 100 % de couverture signifie que tout a été exécuté, pas que tout a été vérifié
◦ Exemple : rappel de numZero (chapitre 7) : le test [2, 7, 0] exécute 100 % des instructions et des branches, mais le défaut 
(boucle qui commence à 1) n'est pas révélé

Graphe de flot de contrôle : définitions
Graphe de flot de contrôle (GFC)
◦ Graphe orienté qui représente tous les enchaînements possibles des instructions d'une fonction
◦ Nœud : bloc d'instructions exécutées en séquence, sans branchement ; nœud de décision : instruction à deux 
sorties (V / F)
◦ Arête : transfert de contrôle d'un nœud à un autre ; un seul nœud d'entrée et un seul nœud de sortie
Chemin
◦ Suite d'arêtes qui va du nœud d'entrée au nœud de sortie
◦ Chemin faisable : il existe une entrée qui le fait parcourir ; sinon, chemin infaisable
◦ Exemple : dans une fonction qui teste « total >= 100 » puis « total < 50 », le chemin qui prend les deux branches V est 
infaisable

Graphe de flot de contrôle : sensibiliser un chemin
Sensibiliser un chemin = trouver une entrée qui le fait parcourir
◦ 1. Choisir le chemin dans le graphe
◦ 2. Écrire son prédicat : la conjonction des conditions rencontrées, en tenant compte des affectations faites en 
chemin
◦ 3. Résoudre le prédicat => données de test ; puis calculer le résultat attendu à partir de la spécification
◦ Exemple : chemin 1-2-3-4-6 (D1 vraie, D2 fausse) : adherent ET total ≥ 100 ET points < 500 ET total ×0,10 ≤ 15, donc 100 
≤ total ≤ 150
◦ Exemple de test : cas de test retenu : adhérent, 120 DT, 0 point => remise de 12 DT, montant attendu 108 DT
Remarque : remise n'est pas une entrée ; le prédicat doit l'exprimer en fonction des entrées

=== PAGE 14 ===
Graphe de flot de contrôle : chemins infaisables
Pourquoi des chemins sont infaisables
◦ Des conditions dépendent les unes des autres : le prédicat du chemin est contradictoire
◦ Exemple : dans l’exemple, si D1 est fausse alors remise vaut 0 : « remise > 15 » ne peut pas être vraie. D2 n'est vraie, 
après D1 fausse, que grâce aux points
Conséquences
◦ 100 % d'un critère est parfois impossible : on exclut les éléments infaisables du calcul, en le justifiant
◦ Savoir si un chemin est faisable est indécidable en général => analyse humaine ou outillée
Outils qui sensibilisent les chemins automatiquement
◦ Exécution symbolique ou concolique (KLEE, Symbolic PathFinder) ; génération par recherche (EvoSuite en Java, 
Pynguin en Python)

Couverture des instructions : définition
Test des instructions (ISTQB)
◦ Éléments à couvrir : les instructions exécutables du code
◦ Couverture des instructions = instructions exécutées par les tests / instructions exécutables
◦ 100 % : chaque instruction a été exécutée au moins une fois
Sur l’exemple
◦ Un seul test exécute les 6 nœuds du graphe, donc toutes les instructions
◦ Exemple de test pour 100 % des instructions : adhérent, 200 DT, 0 point => remise 20 DT, puis bonus de 5 DT car la 
remise dépasse 15 DT ; montant attendu 175 DT
Un seul test, et pourtant D1 et D2 n'ont jamais été fausses

Couverture des branches : définition
Test des branches (ISTQB CTFL v4.0)
◦ Branche : transfert de contrôle entre deux nœuds du graphe. Elle est conditionnelle (une issue V ou F d'une 
décision) ou inconditionnelle (passage en séquence)
◦ Couverture des branches = branches exercées / branches du graphe
Propriété
◦ 100 % des branches => 100 % des instructions, mais pas l'inverse : la couverture des branches subsume celle des 
instructions
Vocabulaire
◦ D'autres références (anciens syllabus, DO-178C) parlent de couverture des décisions : seules les issues des 
décisions sont comptées
◦ Les pourcentages diffèrent, mais 100 % des branches et 100 % des décisions sont atteints par les mêmes tests

Conditions et décisions : vocabulaire
Décision
◦ Expression booléenne qui choisit une branche : celle d'un if, d'un while, d'un for...
Condition
◦ Expression booléenne élémentaire, sans opérateur logique ; une décision combine une ou plusieurs conditions 
avec ET, OU, NON
◦ Exemple : D1 = adherent && total >= 100 contient deux conditions : C1 = adherent, C2 = total >= 100. D2 = points >= 500 
|| remise > 15 contient C3 et C4
Évaluation en court-circuit
◦ En Java (&&, ||) et en Python (and, or), l'évaluation s'arrête dès que le résultat est connu
◦ Si adherent est faux, total >= 100 n'est pas évaluée. Les opérateurs & et | de Java évaluent toujours les deux côtés

=== PAGE 31 ===
Conditions multiples : limites
Coût exponentiel
◦ 2 conditions => 4 combinaisons ; 5 conditions => 32 ; 10 conditions => 1 024
Combinaisons impossibles
◦ Quand les conditions sont liées, certaines combinaisons sont infaisables
◦ Exemple : total >= 100 && total <= 150 : la combinaison (F, F) est impossible ; un total ne peut pas être à la fois inférieur 
à 100 et supérieur à 150
Avec le court-circuit
◦ Les combinaisons à considérer sont celles des conditions réellement évaluées : pour A && B && C, 4 cas au lieu de 
8
Réservé aux décisions de 2 ou 3 conditions. Au-delà : MC/DC

=== PAGE 32 ===
MC/DC : définition
Modified Condition/Decision Coverage
◦ Chaque condition et chaque décision prend les valeurs V et F
◦ Et chaque condition montre qu'elle influence seule le résultat de la décision
Paire d'indépendance
◦ Deux tests où seule cette condition change, les autres restant fixes, et où le résultat de la décision change
◦ Exemple : pour C2 dans D1 : (adhérent, 200 DT) donne V et (adhérent, 50 DT) donne F ; seule C2 a changé, et la décision 
aussi
Coût
◦ Entre n + 1 et 2n tests pour une décision de n conditions, au lieu de 2n
◦ Exemple : 10 conditions : 11 tests au minimum en MC/DC, contre 1 024 en conditions multiples

MC/DC : la méthode sur un exemple
◦ Règle : la livraison express est proposée si l'article est en stock (A) ET si le client est adhérent (B) OU commande au moins 100 DT (C) 
=> A ∧ (B ∨ C)
◦ On écrit la table de vérité, puis on cherche les paires d'indépendance de chaque condition
N° A B C Express Paires d'indépendance
1 F F F F —
2 F F V F A avec 6
3 F V F F A avec 7
4 F V V F A avec 8
5 V F F F B avec 7 ; C avec 6
6 V F V V A avec 2 ; C avec 5
7 V V F V A avec 3 ; B avec 5
8 V V V V A avec 4
Jeu minimal : {2, 5, 6, 7} ou {3, 5, 6, 7} => 4 tests = n + 1, au lieu de 8

MC/DC en pratique
Où MC/DC est exigée
◦ Aéronautique : DO-178C, pour le logiciel de niveau A, dont la défaillance serait catastrophique (niveau B : 
décisions ; niveau C : instructions)
◦ Automobile : ISO 26262, fortement recommandée pour le niveau ASIL D
Court-circuit
◦ Dans une paire, une condition non évaluée (court-circuit) ou sans effet sur le résultat peut varier : c'est la MC/DC 
« par masquage », acceptée par la DO-178C
Outils
◦ Libres : GCC 14 (option -fcondition-coverage) et Clang 18 (option -fcoverage-mcdc) pour C et C++
◦ Commerciaux, qualifiés pour la certification : VectorCAST, LDRA, RapiCover
◦ JaCoCo et coverage.py ne mesurent pas MC/DC

Test de mutation : principe
Idée (DeMillo, Lipton et Sayward, 1978)
◦ Introduire volontairement une petite faute dans le code : chaque version modifiée est un mutant
◦ Exécuter la suite de tests sur chaque mutant : si au moins un test échoue, le mutant est tué ; sinon, il survit
◦ Score de mutation = mutants tués / (mutants générés − mutants équivalents)
Deux hypothèses
◦ Programmeur compétent : le code est proche du code correct ; les fautes réelles sont de petites erreurs
◦ Effet de couplage : des tests qui détectent les fautes simples détectent aussi la plupart des fautes complexes
La mutation évalue les tests, pas le code : un mutant survivant désigne une vérification qui manque

Le problème de l'oracle en boîte blanche
Rappel
◦ L'oracle donne le résultat attendu ; sans oracle, un test exécute le code mais ne vérifie rien
Le piège de la boîte blanche
◦ Les données de test viennent du code ; le résultat attendu, lui, doit venir de la spécification
◦ Un résultat attendu recopié depuis l'exécution du code décrit ce que fait le code, pas ce qu'il devrait faire => le 
test valide les défauts
Qui tombe dans ce piège ?
◦ Les générateurs de tests (EvoSuite, Pynguin, Randoop) : leurs assertions enregistrent le comportement actuel => 
utiles pour la non-régression
◦ Une IA à qui l'on donne seulement le code : même effet
Le code ne peut pas être son propre oracle

static Map<String, Integer> fusionnerListes(
        Map<String, Integer> a,
        Map<String, Integer> b) {
    Map<String, Integer> resultat = new HashMap<>(a);
    for (var e : b.entrySet()) {
        String produit = e.getKey();
        int qte = e.getValue();
        if (resultat.containsKey(produit)) {
            int somme = resultat.get(produit) + qte;
            resultat.put(produit, Math.min(somme, 99));
        } else {
            resultat.put(produit, qte);
        }
    }
    return resultat;
}
def fusionner_listes(a: dict[str, int],

            somme = resultat[produit] + qte
            resultat[produit] = min(somme, 99)
        else:
            resultat[produit] = qte
    return resultat
